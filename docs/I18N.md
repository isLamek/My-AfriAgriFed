# Languages on AfriAgriFed

The site can be shown in more than one language. This page explains how it works, how to add
text or a language, and how we make sure nothing is missing or wrong.

**Where things stand** (branch `i18n`, 15 November 2026):

| Language | Status | What it needs |
|---|---|---|
| English | the source language, complete | nothing |
| Afrikaans (`af`) | **complete, marked "beta"**: 1,900 texts, every placeholder checked by tests | a native speaker's read-through (see "Getting a translation checked") |
| Oshiwambo (`ng`) | not started | a translator and a decision on which dialect (Oshikwanyama or Oshindonga, or both); see below |
| Otjiherero (`hz`) | not started | a translator |

A language only shows up in the language picker once it is listed in
`src/i18n/languages.js` **and** its catalog passes the tests. The picker is hidden while only
English is listed.

## How it works (the short version)

- Every word a person reads lives in a **catalog**, one file per language:
  `src/i18n/locales/en.js` (the source), `af.js`, and so on. One line per text:

  ```js
  "demand.pledgedBy_one": "{pledged} / {needed} {unit} pledged by {count} producer", // progress under a request
  ```

- Code asks for a text by its key: `t("demand.pledge")`, or with values
  `t("demand.postedBy", { name })`. If a language has no text for a key, the visitor sees the
  English one (never a blank, never the raw key).
- `{curly}` placeholders are filled in with names, numbers and so on. A translator may move
  them around the sentence but must keep each one.
- `key_one` / `key_other` pairs are for counts: `_one` is used for exactly 1, `_other` for
  every other number.
- Sentences that contain a link or bold word use `tRich("key", { link: <Link>..</Link> })`, so
  the order of the words can change per language.
- **Saved data stays in English.** A farmer who picks "Local markets" in the questionnaire
  stores `Local markets`; the screen shows it through `tv("Local markets")`, which looks up
  `opt:Local markets` in the visitor's language. So a buyer reading in Afrikaans and a farmer
  writing in English never disagree about what is stored, and reports and the database stay
  consistent.
- Dates, numbers and prices follow the visitor's language (`formatDate`, `formatNumber`):
  `N$1,234.50` in English, `N$1 234,50` in Afrikaans.
- Notifications are stored as a key plus values (`notif.order.confirmed` + `{product}`), so
  the person who receives one reads it in **their** language, not the sender's.
- The AI assistant is told the visitor's language (Afrikaans; for Oshiwambo and Otjiherero it is
  told to answer in plain English unless it is sure of its Oshiwambo/Otjiherero).
- The contact-protection filter (phone numbers, e-mails, links, bank details in chat) knows the
  number words and bank terms of each language, so spelling a number out in Afrikaans does not
  get round it. **Every new language needs its number words added** in `src/contactGuard.js`
  and tests in `src/contactGuard.test.js`.

## What is NOT translated, on purpose

- The Terms, Privacy, Refund and Cookie policy pages: they are legal text and need a qualified
  legal translator. They stay English, and the footer says nothing misleading about that.
- The Admin area (`/admin...`) and the staff tools.
- What members typed: names, posts, comments, product names, notes. See "Translating posts".
- Names of places, towns and regions, the brand name, `N$`.
- Technical credits on the map (data sources).

## Adding or changing text (everyone)

1. Add the English text to `src/i18n/locales/en.js` (or use `node scripts/i18n/add.js file.json`).
2. Use it in the component with `t("group.key")`.
3. Run the checks (below). They fail if the key is missing, or if a switched-on language does
   not have its translation yet.
4. Translate it: `node scripts/i18n/lang.js todo af` lists what is missing; write the texts
   into a JSON file and `node scripts/i18n/lang.js apply af file.json` adds them (it refuses a
   text that loses a `{placeholder}`).

Never build a sentence from pieces (`t("a") + " " + t("b")`): other languages put the words in
another order. Use one key with placeholders.

## The checks (run on every `npm test`)

| Check | Where | It catches |
|---|---|---|
| Every `t("key")` in the code exists | `src/i18n/catalog.test.js` | typos; text that would show as a raw key |
| No text typed into the markup | `src/i18n/catalog.test.js` | a sentence or label added without a key (JSX text, `placeholder`, `title`, `aria-label`, `alt`, toasts, confirm boxes) |
| Switched-on languages are complete | `src/i18n/catalog.test.js` | a missing translation, a dropped `{placeholder}`, an empty text |
| Engine behaviour | `src/i18n/core.test.js` | fallback to English, plurals, `{placeholders}`, rich text |
| Afrikaans contact filter | `src/contactGuard.test.js` | spelled-out numbers and bank words in Afrikaans |
| Translation feature | `src/translate/translate.test.js` | detection, chunking, provider order, limits, timeouts |

Tools (all in `scripts/i18n/`):

| Command | Use |
|---|---|
| `node scripts/i18n/missing-keys.js` | keys the code asks for that English does not have |
| `node scripts/i18n/unused-keys.js` (`--delete`) | texts nothing uses any more |
| `node scripts/i18n/lang.js status af` | how much of a language is done |
| `node scripts/i18n/lang.js check af` | placeholders, empties, missing |
| `node scripts/i18n/lang.js csv af out.csv` | a spreadsheet for a native-speaker review |
| `node scripts/i18n/lang.js import af reviewed.csv` | bring the reviewed spreadsheet back |
| `scripts/i18n/pseudo-scan.js` | finds English still on a screen (see next) |

### Finding English that is still on a page

In a development build (`npm run start:local`), pick **Pseudo (testing)** in the language
picker: every catalog text is shown inside brackets, like `⟦Save⟧`. Anything on screen
**without** brackets is text that never went through the catalog. Paste
`scripts/i18n/pseudo-scan.js` into the browser console on a page: it lists those texts. Names
and member-written text are expected there; everything else is a bug. This was run on every
page for farmers, buyers and institutions before Afrikaans was switched on.

## Getting a translation checked (do this before calling a language "reviewed")

A translation written without a native speaker is **beta**. The picker says so ("This
translation is new. If something reads wrong, please tell us.") and `status: "beta"` in
`languages.js` keeps that note on.

1. `node scripts/i18n/lang.js csv af docs/i18n/review/af.csv`
2. Give the CSV to a native speaker (Google Sheets or Excel opens it). They read the
   `English` column and fix the `af` column; the `where it appears` column says which screen
   it is for. Show them `docs/i18n/GLOSSARY.md` so repeated words stay the same.
3. `node scripts/i18n/lang.js import af reviewed.csv` reads it back (and refuses broken
   placeholders). Run the tests.
4. Change the language's `status` to `"reviewed"` in `src/i18n/languages.js`: the "new
   translation" note disappears.

Things a reviewer should look at first: the registration agreement
(`register.legalComplianceText`), the notifications (`notif.*`), the order steps, and the
Demand Board explanations.

## Adding a language

1. Create `src/i18n/locales/<code>.js` (start with `node scripts/i18n/lang.js todo <code>`).
2. Import it in `src/i18n/locales/index.js` and list it in `src/i18n/languages.js` (code,
   name, how it names itself, `locale` for dates and numbers, `status: "beta"`, plural rule,
   `mt` = whether a free machine translator can read it).
3. Add its **number words** and **bank terms** to `src/contactGuard.js` and tests.
4. Add the compass letters (`compass.*`), month names (`opt:January` ...) and the words in
   `GLOSSARY.md`.
5. Check the date/number format looks right in `Intl` for that locale; if the browser has no
   data for it, use the nearest one in `locale`.
6. Run the tests, the pseudo scan, and look at the sign-in page, the dashboard, the
   questionnaire and a phone-width screen. Longer words can break a layout.
7. Get it reviewed (above).

Oshiwambo has two main written forms (Oshikwanyama and Oshindonga). Decide with the people
you serve which to write first, or whether the site needs both, **before** translating.
There is no free machine translation for Oshiwambo or Otjiherero, so those texts must be
written by people.

## Translating posts

Under a post, comment, Demand Board request, discussion message or research summary, a small
**Translate** button appears when the text is clearly English or Afrikaans and different from
the reader's language. It shows the translation with "Translated from ... by a machine. It
can contain mistakes." and a **Show original** button. Nothing is stored: the translation is
made when someone presses the button and is remembered on that device.

How it translates (`src/translate/`):

1. The browser's own translator, if the language pack is already on the device (the text
   never leaves the device).
2. Otherwise **MyMemory** (translated.net), a free online service that reads English and
   Afrikaans. The text of that one post is sent to them. Their free allowance is limited per
   day; when it runs out the reader sees a clear message.

What it cannot do: **Oshiwambo and Otjiherero**. No free translator reads them, so posts in
those languages show no button (the site will not offer a nonsense translation), and readers
who choose those languages get English as the translation target.

Never used for private messages (Messages), because the text may leave the device.

Settings (`.env`): `REACT_APP_TRANSLATE_PROVIDER=auto` (default), `browser` (never send
anything out), or `off` (no translate button at all).

If you want better coverage later, a self-hosted translation service (LibreTranslate) behind
the backend is the next step; it also has no Oshiwambo or Otjiherero.
